# Chat History Storage Plan

## Goal

Persist AI chat conversations and messages to SQLite so that:
1. Chat history survives app restart
2. Conversations can be listed, browsed, deleted
3. `reasoning_content` (DeepSeek thinking chain) is stored separately for future UI
4. Schema is export-ready (future: Markdown/JSON/PDF export)

## Scope / Non-goals

**In scope:**
- Rust crate `oasis-chat` with SQLite tables `conversations` + `messages`
- Tauri commands for CRUD operations
- Frontend store refactor to call backend instead of in-memory-only
- `reasoning_content` separate field in messages
- Load conversations on mount, save after stream completes

**Out of scope (future work):**
- Export functionality (Markdown/JSON/PDF) — schema is designed to support it but UI not built yet
- Search across conversations
- Conversation folders/tags
- System prompt management

## Current State And Constraints

- Chat data is entirely in-memory via Pinia store (`src/store/chat.ts`) — lost on app restart
- Existing pattern: `oasis-credential` crate uses SQLite via `rusqlite` (bundled), `db.rs` + `models.rs` + `commands.rs`
- DB files stored in `app_data_dir` (via `app.path().app_data_dir()`)
- Tauri command registration is code-generated by `build.rs` scanning `#[tauri::command]`
- `rusqlite` is already a workspace dependency (bundled feature)
- LLM service uses `#[async_trait(?Send)]`, requires `LocalSet` + current-thread runtime for stream commands
- `StreamChunk` currently sends `content: string` only — needs `reasoning_content` field
- Frontend `ChatMessage` interface has `role: 'user' | 'assistant' | 'system'`, `content`, `streaming`, `error`

## Design

### 1. Database Schema

Two tables in `chat.db` (separate from `credentials.db`):

```sql
CREATE TABLE IF NOT EXISTS conversations (
    id          TEXT PRIMARY KEY,          -- UUID from frontend
    title       TEXT NOT NULL DEFAULT '新对话',
    model_id    TEXT NOT NULL DEFAULT '',
    created_at  TEXT NOT NULL,             -- ISO 8601
    updated_at  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS messages (
    id                  TEXT PRIMARY KEY,  -- UUID from frontend
    conversation_id     TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    role                TEXT NOT NULL,     -- 'user' | 'assistant' | 'system'
    content             TEXT NOT NULL DEFAULT '',
    reasoning_content   TEXT,              -- DeepSeek thinking chain, nullable
    token_usage         TEXT,              -- JSON: {"promptTokens":..,"completionTokens":..,"totalTokens":..}
    created_at          TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_messages_conversation ON messages(conversation_id);
CREATE INDEX IF NOT EXISTS idx_conversations_updated ON conversations(updated_at DESC);
```

**Key design decisions:**
- `id` is TEXT (UUID) — frontend generates IDs, Rust stores them as-is. Avoids auto-increment mismatch.
- `reasoning_content` is nullable — only present for assistant messages from reasoning models.
- `token_usage` stored as JSON TEXT — avoids extra table, easy to parse for export.
- `ON DELETE CASCADE` — deleting a conversation removes all messages.
- Separate `chat.db` from `credentials.db` — different concern, no encryption needed for chat.

### 3. Models (`models.rs`)

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct Conversation {
    pub id: String,
    pub title: String,
    pub model_id: String,
    pub created_at: String,
    pub updated_at: String,
}

#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct Message {
    pub id: String,
    pub conversation_id: String,
    pub role: String,              // "user" | "assistant" | "system"
    pub content: String,
    pub reasoning_content: Option<String>,
    pub token_usage: Option<String>, // JSON string
    pub created_at: String,
}

// Frontend-friendly: conversation with its messages
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct ConversationDetail {
    pub conversation: Conversation,
    pub messages: Vec<Message>,
}

// For list view: conversation + message count
#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct ConversationListItem {
    pub id: String,
    pub title: String,
    pub model_id: String,
    pub message_count: i64,
    pub created_at: String,
    pub updated_at: String,
}
```

### 4. Tauri Commands (`commands.rs`)

| Command | Signature | Description |
|---|---|---|
| `list_conversations` | `(app) -> Vec<ConversationListItem>` | List all, sorted by updated_at DESC |
| `get_conversation` | `(app, id) -> ConversationDetail` | Get conversation + all messages |
| `create_conversation` | `(app, id, title, model_id) -> Conversation` | Create with frontend-generated UUID |
| `save_message` | `(app, message) -> Message` | Insert one message |
| `save_messages` | `(app, messages: Vec<Message>) -> Vec<Message>` | Batch insert (after stream ends) |
| `update_conversation_title` | `(app, id, title) -> ()` | Rename |
| `delete_conversation` | `(app, id) -> ()` | Delete + cascade messages |
| `update_message_content` | `(app, id, content, reasoning_content?) -> ()` | Update message after stream |

## Risks And Compatibility

- **Pre-existing TS errors**: `ChatView.vue` has a type error on `role` (`"system"` not assignable to `"user" | "assistant"`). Our changes will fix this by aligning the type.
- **DB migration**: New `chat.db` — no migration needed since it's a new file. If `chat.db` exists from a previous partial implementation, `CREATE TABLE IF NOT EXISTS` handles it.
- **Performance**: Loading all conversations on mount is fine for typical usage (<1000 conversations). Lazy message loading per conversation prevents large payloads.
- **Stream interruption**: If app crashes mid-stream, the user message is saved but assistant message is not. Acceptable trade-off vs. per-token DB writes.
